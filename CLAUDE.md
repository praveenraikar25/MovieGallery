# MovieGallery

Android app (package `com.raikar.moviegallery`), moving to Kotlin Multiplatform: `:app` is the Android application, `:shared` is a KMP library (Android, `iosArm64`, `iosSimulatorArm64`) holding the code both platforms use, and `iosApp/` is the SwiftUI iOS app that consumes it (Login and Home so far; the other screens are phase 5c).

## Tech Stack

Always use the latest stable Android tech stack. Concretely:

- **Kotlin & AGP**: target the latest stable Kotlin and Android Gradle Plugin versions. `gradle/libs.versions.toml` is the single source of truth for all dependency/plugin versions — add new versions there, don't hardcode them in module `build.gradle.kts` files.
- **UI**: Jetpack Compose with Material 3 for all Android UI. Do not add new XML layouts or View-based Activities/Fragments. iOS UI is SwiftUI (iOS 17+), on the shared ViewModels; Swift holds no business logic or user-facing copy the shared code already has.
- **DI**: Koin, plain DSL only (`module { }`, `single`/`factory`, `singleOf`/`factoryOf`/`viewModelOf`). No Koin annotations or compiler plugin, so a Kotlin upgrade never waits on a DI release. Classes carry no DI annotations; on Android, ViewModels are resolved with `koinViewModel()`.
- **Networking/async**: Ktor for REST calls (OkHttp engine on Android, Darwin on iOS), Apollo Kotlin for GraphQL, Kotlin Coroutines/Flow for async data. Repositories expose main-safe suspend functions / `Flow`; ViewModels expose `StateFlow`.
- **Persistence**: Room 3 (`androidx.room3`, not Room 2's `androidx.room`) for on-device data. DAOs return `Flow` / suspend; schemas are exported to `shared/schemas/` and committed, and there is no destructive fallback — a schema change needs a real `Migration`, registered once in the shared `MIGRATIONS` list (`data/local/MovieGalleryDatabaseFactory.kt`).
- **Dependencies**: when adding any new library, use its latest stable release and add it via the version catalog. The one exception is the iOS app's Swift packages (the Firebase iOS SDK), which Xcode resolves and pins in `iosApp/iosApp.xcodeproj/project.xcworkspace/xcshareddata/swiftpm/Package.resolved`, which is committed.

## Code style

Kotlin formatting is enforced by ktlint (`org.jlleitschuh.gradle.ktlint`), configured via the root `.editorconfig` (`ktlint_official` style, 120-column limit).

- `./gradlew ktlintCheck` — verify; `./gradlew ktlintFormat` — auto-fix.
- **Once per clone**: run `./gradlew installGitHooks` to point git at `.githooks/`. The `pre-commit` hook then formats staged Kotlin, re-stages the fixes, and blocks the commit on anything ktlint can't auto-fix. Bypass with `SKIP_KTLINT=1 git commit` or `--no-verify`.

For layering and module structure (Clean Architecture: UI / Domain / Data, multi-module strategy), see `.claude/skills/android-architecture/SKILL.md` — keep that skill and this file in sync rather than duplicating details here.

## Commands

- `./gradlew assembleDebug` — build; `./gradlew test` — all JVM unit tests (no instrumented tests of note). Room DAO/repository tests run under Robolectric against a real database built with the production builder (`testutil/TestDatabases.kt`; `DatabaseUpgradeTest` pins the file existing installs have), with `@Config(application = Application::class)` so the app's Firebase setup isn't started.
- Single test: `./gradlew :shared:testAndroidHostTest --tests "com.raikar.moviegallery.ui.screens.home.HomeViewModelTest"` (append `.methodName` for one method). `:app` tests: `./gradlew :app:testDebugUnitTest --tests "…"`.
- `./gradlew test` includes `:shared`'s JVM tests (its `test` task wraps `testAndroidHostTest`). iOS runs separately: `./gradlew :shared:iosSimulatorArm64Test` (needs Xcode and an iOS simulator runtime). `./gradlew :shared:linkDebugFrameworkIosSimulatorArm64` builds the static `Shared` framework the iOS app links; its Objective-C header (`shared/build/bin/iosSimulatorArm64/debugFramework/Shared.framework/Headers/Shared.h`) shows what Swift sees.
- `:shared` common code must compile for iOS: no `android.*`, `java.*` or `javax.*` imports in `commonMain`/`commonTest`, and test names can't contain `,` `.` `:` `;` (Kotlin/Native rejects them). Check with `./gradlew :shared:compileKotlinIosSimulatorArm64`.

- iOS app: `xcodebuild -project iosApp/iosApp.xcodeproj -scheme iosApp -destination 'platform=iOS Simulator,name=iPhone 17,OS=26.5' -derivedDataPath iosApp/build build` (swap `build` for `test` to run `iosAppTests`). The scheme's "Build Shared framework" phase runs `./gradlew :shared:embedAndSignAppleFrameworkForXcode` first, so Kotlin changes are picked up without a separate Gradle step. Name an iPhone that exists on the latest installed iOS runtime (`xcrun simctl list devices available`); `xcodebuild` defaults to the latest OS.

## Build prerequisites

- `app/google-services.json` must exist — the google-services plugin is applied unconditionally, so the build fails without it.
- TMDB v4 token comes from the `TMDB_READ_ACCESS_TOKEN` env var, else `tmdb.readAccessToken` in `local.properties` (git-ignored; do not read or edit it — denied in `.claude/settings.json`). It is injected as a `BuildConfig` field via the variant API (not `buildConfigField`, removed in AGP 10). Without it the build still works but TMDB calls return 401.
- AI chat additionally needs Firebase AI Logic + an App Check debug token; other features don't.
- iOS app (`iosApp/`): needs `iosApp/iosApp/GoogleService-Info.plist` from an iOS app registered in the same Firebase project with bundle ID `com.raikar.moviegallery` (git-ignored; `FirebaseApp.configure()` stops the app at launch without it), and the TMDB token in `iosApp/Configuration/Secrets.xcconfig` (git-ignored; copy `Secrets.example.xcconfig`; without it the app builds and TMDB returns 401). AI on iOS needs the simulator's App Check debug token, which the debug console prints at launch, registered in the Firebase console. Do not read or print either file's contents.
- Sign-in needs the Email/Password and Google providers enabled in the Firebase console, your debug SHA-1 registered, and `app/google-services.json` re-downloaded so it carries an OAuth web client (the google-services plugin turns it into `default_web_client_id`).

## Backends

`:shared`'s `networkModule` provides two Ktor `HttpClient`s selected by the Koin qualifiers in `di/Qualifiers.kt`, each on its own engine from the platform's engine factory (on Android, OkHttp over the shared base `OkHttpClient`): `TmdbClient` (`TmdbApi`, movies, bearer-token auth) and `BffClient` (`BffApi`, TV shows, a separate demo host). They are built by `createTmdbHttpClient` / `createBffHttpClient` (`:shared` `data/remote/HttpClients.kt`) from a `NetworkConfig` (token, app version, log level) that `:app` builds from `BuildConfig`. The BFF client installs the `BffAuth` plugin (`data/remote/auth/`): a fresh Firebase ID token on every request, no request without one, and one force-refreshed retry on a 401 from the BFF host. New endpoints must pick the right client; base URLs need a trailing slash and request paths have no leading slash. Wrap calls in `safeApiCall`, which maps Ktor failures to `AppError`s. On iOS the bridges are implemented in Swift (`iosApp/iosApp/Platform/`): `FirebaseAuthService` passes each `NSError`'s domain, code and description through untouched, and `FirebaseAiService` builds the model from `ChatModelConfig` and sorts SDK errors into `AiFailureKind` (`aiFailureKind`); neither decides what an error means. Authentication is a third, non-HTTP-client backend: Firebase Auth, reached through `AuthRepository` and mapped to `AuthError` by `safeAuthCall` (`data/remote/auth/`). The Google ID token comes from Credential Manager in the UI layer (`ui/screens/login/GoogleSignIn.kt`) because it needs an Activity; only the token string crosses into the repository. On iOS, Firebase Auth and Firebase AI are reached through Swift: `:shared` `iosMain` `platform/` declares `FirebaseAuthBridge` and `FirebaseAiBridge`, the iOS app implements them with the Firebase iOS SDK, and `IosAuthRepository` / `IosAuthTokenProvider` / `IosAiChatRepository` build on them, mapping errors with `mapBridgedAuthError` / `mapBridgedAiFailure` (`iosMain` `data/remote/auth/`, `data/remote/ai/`) to the same `AuthError`s / `AppError`s Android's `safeAuthCall` / `safeAiCall` give. The Gemini model name, timeout and prompts both apps send are `ChatModelConfig` (`commonMain` `data/remote/ai/`), and both chat repositories reject an empty reply with `requireReplyText`.

The fourth backend is GraphQL: the public, unauthenticated Countries API, reached through the single `ApolloClient` in `:app`'s `androidPlatformModule` (derived from the shared base `OkHttpClient`; no qualifier while it is the only Apollo client). Its schema and `.graphql` operations live in `shared/src/commonMain/graphql/countries/`, and Apollo generates typed models into `data/remote/graphql/countries` at build time — they stay in the data layer. Apollo returns failures on the response instead of throwing, so wrap calls in `safeGraphQlCall`, which maps them to the same `AppError`s as `safeApiCall`. `CountryRepository` backs the production-country details sheet on Movie Detail.

## Repo map

Source lives in two modules, with the same `com.raikar.moviegallery.*` packages in both:

- `:shared` — `shared/src/commonMain/kotlin/com/raikar/moviegallery/` (per-platform `actual`s in `androidMain/` and `iosMain/`): all of `domain/`; from `data/`, the DTOs and mappers, `TmdbGenres`/`TmdbImages`, `local/` (Room), the Countries GraphQL code, the Ktor networking (`TmdbApi`, `BffApi`, the client factories, `NetworkConfig`, `BffAuth`, `safeApiCall`), the movie, TV-show, watchlist and country repositories, and `di/` (the shared Koin modules and qualifiers); from `ui/`, every ViewModel and UiState (`ui/screens/<feature>/`, `ui/navigation/AppSessionViewModel.kt`) and, in `iosMain/`, the Swift bridge (`ui/bridge/`: `StateFlowWatcher` delivers a `StateFlow` to a Swift closure on the main thread, `ViewModelOwner` holds a ViewModel and clears it) and the iOS platform layer: `di/IosPlatformModule.kt` (`iosPlatformModule`, `IosAppConfig`), `di/IosKoin.kt` (`startMovieGallery`, `MovieGalleryGraph`), the Firebase bridges in `platform/` and their adapters (`data/repository/IosAuthRepository.kt`, `IosAiChatRepository.kt`, `data/remote/auth/IosAuthTokenProvider.kt`). Tests: `shared/src/commonTest/` (plain Kotlin, `kotlin.test`, runs on JVM and iOS; ViewModel tests set `Dispatchers.setMain` in `@BeforeTest` and use the repository fakes in `testutil/`; network tests use the `MockEngine`-backed `FakeHttpServer` and `testutil/TestBackends.kt`, with JSON fixtures as strings in `data/remote/TestFixtures.kt`) and the JVM-only `androidHostTest/` and iOS-only `iosTest/` (each with a real-engine `RealEngineNetworkErrorTest`; `iosTest/` also has `WatchlistDaoIosTest`, Room on the iOS driver, `ViewModelBridgeTest`, `IosKoinGraphTest` (the whole iOS graph resolves, offline), and `IosAuthRepositoryTest` / `IosAiChatRepositoryTest` over the fake bridges in `iosTest/.../testutil/`).
- `:app` — `app/src/main/java/com/raikar/moviegallery/`: the Compose UI (screens, `ui/components`, `ui/theme`, navigation), the Android Koin modules in `di/`, and the data code still tied to the JVM or Android — `auth/` (Firebase Auth), `ai/`, and the auth and AI repositories. Tests needing Robolectric, MockWebServer, MockK or classpath JSON fixtures stay in `app/src/test/` (its `testutil/FakeAuthRepository` is a copy of the shared fake, kept only for the Robolectric watchlist tests).
- `iosApp/` — the SwiftUI app. `iosApp.xcodeproj` uses synchronized folders, so new Swift files in `iosApp/iosApp/` or `iosApp/iosAppTests/` join their target without a project-file change; `Configuration/Config.xcconfig` holds the framework search path, `-framework Shared -lsqlite3`, the version and the token default. `iosApp/iosApp/`: `MovieGalleryApp.swift` (`AppEnvironment` installs App Check, configures Firebase, then calls `startMovieGallery`; as a test host it starts nothing), `RootView.swift` (Login or Home from `AppSessionViewModel.isSignedIn`), `Platform/` (`AppConfiguration` builds `IosAppConfig` from `Info.plist`; `FirebaseAuthService` and `FirebaseAiService` implement the two bridges), `Shared/ObservedViewModel.swift` (`ObservedViewModel` pairs `ViewModelOwner` with `StateFlowWatcher`; `ViewModelScope` creates it once per screen), and one folder per screen (`Login/`, `Home/`). `iosAppTests/` (XCTest) covers the Swift translation functions and `AppConfiguration`.

The per-package map below applies across both modules:

- `ui/screens/<feature>/` — one package per screen, split across the modules: `<Feature>Screen.kt` (Compose UI, `:app`), `<Feature>ViewModel.kt` (`:shared`; plain constructor, registered in `viewModelModule`, exposes `StateFlow`; navigation arguments are constructor parameters, never `SavedStateHandle`), `<Feature>UiState.kt` (`:shared`). Existing features: `home`, `search`, `detail`, `watchlist`, `profile`, `login`, `chat`, `tvshows`.
- `ui/navigation/` — `Destinations.kt` / `Routes` (route constants), `AppNavHost.kt` (`NavHost` graph), `AppSessionViewModel.kt` (`:shared`; whether a session exists at launch, which `AppNavHost` maps to the start route, and sign-out), `MainScaffold.kt` (bottom nav / tab scaffold for top-level tabs).
- `ui/components/` — shared Compose widgets (cards, chips, buttons, state views) reused across screens.
- `ui/common/` (`:shared`) — user-facing copy both apps show: `ErrorCopy.kt` (`AppError.errorTitle` / `errorDetail`, the full-screen error text) and `MovieLabels.kt` (`Movie.cardSubtitle`). Put new copy that both platforms display here, not in a Compose or SwiftUI file.
- `ui/theme/` — Material 3 theme, color, type, shape, dimens.
- `domain/model/` — plain data classes shared across layers.
- `domain/repository/` — repository interfaces (`<Thing>Repository`), implemented in `data/repository/`.
- `domain/usecase/` — one class per use case, invoked from a ViewModel; wraps a repository call.
- `data/remote/` — `auth/` (`safeAuthCall`, Firebase Auth error mapping), `TmdbApi.kt` / `BffApi.kt` (Ktor calls), `HttpClients.kt` (client factories, `networkJson`), `dto/` (network DTOs), `MovieMappers.kt` (DTO → domain mapping), `SafeApiCall.kt` (network error wrapping), `ai/` (Firebase AI client), `SafeGraphQlCall.kt` + `CountryMappers.kt` (GraphQL error wrapping and Apollo model → domain mapping; generated Apollo code lands in `graphql/countries`).
- `data/repository/` — repository implementations (`<Thing>RepositoryImpl.kt`), or a static/in-memory impl where there's no backing API yet. Shared ones (`WatchlistRepositoryImpl`, `CountryRepositoryImpl`) take plain constructor params, with no annotations.
- `data/local/` — the Room database (`MovieGalleryDatabase`), its DAOs, entities, column converters and entity ↔ domain mappers. It is built in `:shared`: `MovieGalleryDatabaseFactory.kt` (`commonMain`) holds the shared config (`applySharedConfig()`, the `MIGRATIONS` list), and each platform has a `movieGalleryDatabaseBuilder` — Android's from the `Context` with the same file and default driver as ever (never the Context-less overload, which opens a different file), iOS's in Application Support on `NativeSQLiteDriver` (iOS binaries link `-lsqlite3`). The watchlist lives here, keyed by the signed-in account's Firebase uid.
- `di/` — Koin modules, split by where they can live. `:shared` `di/SharedModules.kt`: `networkModule` (the two qualified Ktor clients and APIs), `databaseModule` (`expect`/`actual`: the `MovieGalleryDatabase` single, closed with the graph), `dataModule` (shared repositories, `WatchlistDao`, `kotlin.time.Clock` — injected so tests control timestamps — and the `IoDispatcher` dispatcher), `domainModule` (every use case) and `viewModelModule` (every ViewModel, `viewModelOf`), collected in `sharedModules`, whose KDoc lists what a platform must supply; `di/Qualifiers.kt` holds the `TmdbClient` / `BffClient` / `IoDispatcher` qualifiers. `:app` `di/AndroidModules.kt`: `androidPlatformModule` (base `OkHttpClient`, the engine factory, `NetworkConfig`, `ApolloClient`, Coil `ImageLoader`, Firebase Auth and the auth/token implementations); `di/AiModule.kt`: `aiModule` (Firebase AI model and the chat stack). `MovieGalleryApplication` starts Koin with `sharedModules + androidModules`. `:shared` `iosMain` `di/IosPlatformModule.kt`: `iosPlatformModule` supplies the same for iOS (a Darwin engine factory, `NetworkConfig` from the `IosAppConfig` Swift passes in, Apollo, and the three bridge-backed repositories); Swift starts the graph once with `startMovieGallery(config:authBridge:aiBridge:)` (`di/IosKoin.kt`) and gets ViewModels from the returned `MovieGalleryGraph`. Graph tests: `KoinGraphTest` (`verify()`, constructor parameters) and `KoinGraphResolutionTest` (Robolectric, resolves every use case) in `app/src/test/.../di/`, `SharedModulesTest` (which qualified client each API gets) in `:shared` `commonTest`, and `IosKoinGraphTest` in `:shared` `iosTest`.

## Adding a feature screen

Touch these in order:

1. `domain/model/` (`:shared` `commonMain`) — add/extend the domain model if needed.
2. `domain/repository/<Thing>Repository.kt` (`:shared`) — interface with suspend/`Flow` methods.
3. `data/repository/<Thing>RepositoryImpl.kt` — implementation (or a static impl if there's no API yet). In `:shared` if it only needs multiplatform libraries; in `:app` if it needs Firebase or Android APIs.
4. `di/` — register it as a `single` bound to its interface: in `:shared` `dataModule` for a `:shared` impl, or in `:app` `androidPlatformModule` for an `:app` impl. Use `singleOf(::Impl) bind Repo::class` unless a parameter needs a qualifier (`get(IoDispatcher)`), then an explicit lambda.
5. `domain/usecase/` (`:shared`) — one use case class wrapping the repository call the screen needs, with no annotations, plus a `factoryOf(::XUseCase)` in `domainModule`. Add it to `KoinGraphResolutionTest`'s list.
6. `ui/screens/<feature>/` — in `:shared` `commonMain`: `<Feature>UiState.kt` and `<Feature>ViewModel.kt` (plain constructor taking the use case, exposes `StateFlow<UiState>`, plus a `viewModelOf(::XViewModel)` in `:shared`'s `viewModelModule`; a navigation argument is a constructor parameter, passed with `koinViewModel { parametersOf(arg) }`, never `SavedStateHandle`). In `:app`: `<Feature>Screen.kt` (Compose UI, `koinViewModel()`). In `:shared` `iosMain` `di/IosKoin.kt`: a `MovieGalleryGraph` function returning the ViewModel, so Swift can reach it (`IosKoinGraphTest` fails without one).
7. `ui/navigation/Destinations.kt` — add a route constant.
8. `ui/navigation/AppNavHost.kt` — register the composable route.
9. `ui/navigation/MainScaffold.kt` — add a tab/nav entry if it's a top-level destination.
10. `shared/src/commonTest/kotlin/.../ui/screens/<feature>/` — ViewModel test (`kotlin.test`, `Dispatchers.setMain` in `@BeforeTest`) using a fake repository from `shared/src/commonTest/kotlin/.../testutil/`.

## Adding a TMDB endpoint

1. `data/remote/dto/` (`:shared`) — response DTO(s) matching the TMDB JSON shape.
2. `data/remote/TmdbApi.kt` (`:shared`) — new method: `client.get("path") { parameter(...) }.decode()`.
3. `data/remote/MovieMappers.kt` (`:shared`) — `internal` DTO → domain model mapping function.
4. `domain/repository/` + `data/repository/...Impl.kt` (both `:shared`) — expose the call through the repository layer (wrap with `safeApiCall`).
5. `shared/src/commonTest/.../data/remote/` — add a fixture string to `TestFixtures.kt` and a test against `FakeHttpServer` (see `TmdbApiTest.kt`).

## Adding a GraphQL query

1. `shared/src/commonMain/graphql/countries/` — add a `.graphql` operation; the build validates it against the committed `schema.graphqls` (refresh with `./gradlew :shared:downloadCountriesApolloSchemaFromIntrospection`; regenerate models with `./gradlew :shared:generateCountriesApolloSources`).
2. `data/remote/` (`:shared`) — map the generated `…Query.Data` to a domain model (see `CountryMappers.kt`).
3. `domain/repository/` + `data/repository/...Impl.kt` (both `:shared`) — call `apollo.query(...).execute()` inside `safeGraphQlCall` on an injected dispatcher, and register it in `dataModule` with `get(IoDispatcher)`.
4. Tests — a mapper test with generated models in `shared/src/commonTest/`, and in `app/src/test/java/.../data/` a repository test running a real `ApolloClient` against `MockWebServerRule` with a JSON fixture (see `CountryRepositoryImplTest.kt`).
